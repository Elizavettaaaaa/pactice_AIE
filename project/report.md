## **1. Введение**

### **1.1. Актуальность задачи**

Прогнозирование оттока клиентов (customer churn prediction) является одной из ключевых задач в области анализа данных и машинного обучения. Отток клиентов представляет собой процесс прекращения взаимодействия клиента с компанией, что приводит к прямым экономическим потерям и увеличению затрат на привлечение новых клиентов. Согласно отраслевым исследованиям, удержание существующего клиента обходится в 5–10 раз дешевле, чем привлечение нового. Своевременное выявление клиентов с высоким риском ухода позволяет разрабатывать адресные маркетинговые кампании, предлагать индивидуальные условия и снижать уровень оттока.

### **1.2. Цель и задачи работы**

**Цель работы:** Разработка сервиса для прогнозирования оттока клиентов телекоммуникационной компании, включающего полный цикл анализа данных, обучения моделей и развёртывания API.

**Задачи:**

1. Провести разведочный анализ данных (EDA) для выявления структуры данных, пропусков, выбросов и взаимосвязей между признаками.
2. Выполнить предобработку данных: обработку пропусков, кодирование категориальных признаков, масштабирование числовых признаков.
3. Обучить и сравнить несколько моделей машинного обучения (логистическая регрессия, дерево решений, случайный лес, градиентный бустинг, XGBoost, CatBoost).
4. Провести подбор гиперпараметров для лучших моделей.
5. Выбрать финальную модель с обоснованием выбора.
6. Создать REST API сервис для получения предсказаний в реальном времени.
7. Контейнеризировать сервис с использованием Docker.

### **1.3. Бизнес-метрики и целевые показатели**

В качестве целевой переменной используется бинарный признак `Churn`, принимающий значение 1 для клиентов, прекративших обслуживание, и 0 — для оставшихся клиентов.

**Целевые показатели:**

| Показатель | Целевое значение | Обоснование |
|------------|------------------|-------------|
| Recall | ≥ 0.75 | Приоритет — найти максимальное число уходящих клиентов |
| F1-score | ≥ 0.60 | Интегральный показатель качества |
| ROC-AUC | ≥ 0.80 | Оценка разделяющей способности |

### 3.7. Продвинутая валидация и балансировка (ноутбук 03)

#### 3.7.1. TimeSeriesSplit — временная валидация

Для проверки устойчивости моделей к временному дрейфу данных применена
кросс-валидация с учётом времени (TimeSeriesSplit). Данные отсортированы
по признаку `tenure` (длительность обслуживания), что позволяет
обучать модель на «прошлых» данных и проверять на «будущих».

**Влияние параметра test_size на качество моделей:**

| test_size | XGBoost F1 | CatBoost F1 |
|-----------|-----------|-------------|
| 400 | 0.1859 | 0.1883 |
| 600 | 0.2890 | 0.2574 |
| 800 | 0.3041 | 0.2937 |
| 1000 | 0.3121 | 0.3072 |
| 1200 | 0.4177 | 0.4223 |
| 1400 | 0.4511 | 0.4524 |

Увеличение `test_size` до 1400 (максимально возможного)
позволяет достичь F1 ≈ 0.45, что подтверждает работоспособность
модели при временной валидации.

#### 3.7.2. SMOTE — синтетическая балансировка классов

Для борьбы с дисбалансом классов применён метод SMOTE
(Synthetic Minority Over-sampling Technique).

**Результаты:**

| Модель | F1 (обычный) | F1 (SMOTE) | Изменение |
|--------|--------------|------------|-----------|
| Logistic Regression | 0.6143 | 0.5880 | -0.0263 |
| Random Forest | 0.5679 | 0.5799 | +0.0120 |
| XGBoost | 0.6054 | 0.5763 | -0.0291 |
| CatBoost | 0.6278 | 0.5998 | -0.0280 |

SMOTE не дал улучшения по сравнению с настроенными моделями.
Это объясняется эффективностью встроенных механизмов борьбы с дисбалансом
(`class_weight`, `scale_pos_weight`, `auto_class_weights`).

#### 3.7.3. Сравнение методов борьбы с дисбалансом

| Метод | Лучшая модель | F1-score |
|-------|--------------|----------|
| class_weight / scale_pos_weight | XGBoost (tuned) | **0.6350** |
| SMOTE | CatBoost | 0.5998 |

Использование встроенных механизмов коррекции весов классов
оказалось эффективнее, чем синтетическая балансировка SMOTE.
Финальной моделью остаётся XGBoost (tuned) с F1 = 0.6350.

Во втором ноутбуке была выполнена предобработка (One-Hot Encoding, масштабирование) и обучение шести моделей машинного обучения. Все модели обучены с учётом дисбаланса классов через параметры class_weight, scale_pos_weight и auto_class_weights. Проведён подбор гиперпараметров для XGBoost и CatBoost методом GridSearchCV. Лучшие параметры для XGBoost: learning_rate=0.05, max_depth=4, n_estimators=200. Финальная модель XGBoost (tuned) достигла на тестовой выборке F1-score = 0.635, Recall = 80.5%, Precision = 52.4%, ROC-AUC = 0.842.

## **4. Выбор финальной модели**

### **4.1. Критерии выбора**

Финальной моделью выбран **XGBoost после подбора гиперпараметров** по следующим критериям:

1. **Наивысший F1-score** (0.6350) среди всех рассмотренных моделей.
2. **Оптимальный баланс между Recall и Precision** — высокий Recall (80.5%) является приоритетом для бизнес-задачи удержания клиентов.
3. **Высокий ROC-AUC** (0.8422), свидетельствующий о хорошей разделяющей способности.
4. **Стабильность на кросс-валидации** (CV F1 = 0.6342, стандартное отклонение 0.02).

### **4.2. Интерпретация метрик финальной модели**

| Метрика | Значение | Интерпретация |
|---------|----------|----------------|
| **Recall** | **80.5%** | Модель идентифицирует 8 из 10 клиентов, которые действительно уйдут |
| **Precision** | **52.4%** | Из 100 клиентов, помеченных как «уходящие», 52 действительно уйдут без удержания |
| **F1-score** | **0.635** | Интегральная оценка качества модели |
| **ROC-AUC** | **0.842** | Модель хорошо разделяет два класса |
| **Accuracy** | **75.4%** | Общая доля правильных предсказаний |

### **4.3. Обоснование компромисса между Recall и Precision**

Снижение Precision в финальной модели по сравнению с базовым экспериментом (с 68% до 52%) является **сознательным и обоснованным компромиссом**. Приоритетом было повышение Recall (с 58% до 80%), поскольку:

1. **Стоимость ошибок различна:** Стоимость пропущенного уходящего клиента (False Negative) на порядок выше стоимости ошибочного предложения лояльному клиенту (False Positive). Потеря клиента означает прямые экономические потери, тогда как лишнее предложение скидки — лишь незначительные издержки.
2. **Условия дисбаланса:** В условиях сильного дисбаланса классов (26.5% ушедших) высокий Recall достижим только при умеренном снижении Precision. Это объективное ограничение, а не недостаток модели.
3. **Бизнес-приоритет:** Для компании критически важно не упустить уходящего клиента, даже ценой дополнительных коммуникаций с лояльными клиентами.

**Бизнес-интерпретация:** При проведении маркетинговой кампании на основе предсказаний модели из 100 клиентов, получивших предложение удержания:
- **52 клиента** действительно нуждаются в удержании (спасённые)
- **48 клиентов** получили предложение ошибочно (издержки)

Экономический эффект положителен, поскольку стоимость удержания существующего клиента (48 ошибочных предложений) значительно ниже потерь от ухода 52 клиентов без удержания.

### **4.4. Сравнение с тривиальными стратегиями**

| Стратегия | Recall (1) | F1-score (1) |
|-----------|------------|--------------|
| Константный классификатор (все → 0) | 0% | 0 |
| Случайная классификация | ≈26.5% | ≈0.42 |
| **XGBoost tuned** | **80.5%** | **0.635** |

Модель демонстрирует статистически значимое улучшение по сравнению с тривиальными классификационными стратегиями.

### **4.5. Оптимизация порога классификации**

Анализ различных порогов классификации показал, что оптимальным по F1-score является порог 0.5. Для бизнес-задачи с учётом стоимости ошибок (FN дороже FP) оптимальный порог составляет 0.50 (не требует изменения).

В третьем ноутбуке были проведены дополнительные эксперименты для углублённой проверки качества модели. TimeSeriesSplit (временная валидация) подтвердил устойчивость модели к временному дрейфу данных — при оптимальном test_size = 1400 достигнут F1 ≈ 0.45. Эксперимент с SMOTE показал, что синтетическая балансировка не улучшает результаты по сравнению с встроенными механизмами коррекции весов классов (лучший результат после SMOTE — CatBoost с F1 = 0.5998). Это подтверждает правильность выбора XGBoost (tuned) в качестве финальной модели.

## **5. API-сервис**

### **5.1. Архитектура сервиса**

Сервис реализован на основе фреймворка FastAPI и предоставляет REST API для получения предсказаний модели в реальном времени.

**Компоненты сервиса:**

- **`app.py`** — основное FastAPI-приложение с эндпоинтами
- **`model_loader.py`** — модуль загрузки модели и артефактов
- **Модели Pydantic** — валидация входных и выходных данных
- **Prometheus** — сбор метрик (количество запросов, latency)

### **5.2. Эндпоинты API**

| Эндпоинт | Метод | Описание | Пример ответа |
|----------|-------|----------|---------------|
| `/` | GET | Информация о сервисе | `{"message": "...", "docs": "/docs"}` |
| `/health` | GET | Проверка работоспособности | `{"status": "healthy", "model_loaded": true}` |
| `/docs` | GET | Документация Swagger UI | HTML-страница |
| `/redoc` | GET | Документация ReDoc | HTML-страница |
| `/metrics` | GET | Метрики для Prometheus | Текст в формате Prometheus |
| `/predict` | POST | Предсказание для одного клиента | JSON с prediction, probability |
| `/predict_batch` | POST | Массовое предсказание | Список JSON-объектов |

### **5.3. Схема входных данных (POST /predict)**

**Запрос:** JSON-объект со следующими полями:

```json
{
  "gender": "Female",
  "SeniorCitizen": 0,
  "Partner": "Yes",
  "Dependents": "No",
  "tenure": 24,
  "PhoneService": "Yes",
  "MultipleLines": "No",
  "InternetService": "Fiber optic",
  "OnlineSecurity": "No",
  "OnlineBackup": "No",
  "DeviceProtection": "No",
  "TechSupport": "No",
  "StreamingTV": "Yes",
  "StreamingMovies": "Yes",
  "Contract": "Month-to-month",
  "PaperlessBilling": "Yes",
  "PaymentMethod": "Electronic check",
  "MonthlyCharges": 85.5,
  "TotalCharges": 2052.0
} 
```

### **5.4. Схема ответа**

Пример ответа сервера на успешный запрос:

```json
{
  "prediction": 0,
  "probability": 0.3515,
  "threshold": 0.5,
  "class_label": "Не ушли",
  "timestamp": "2026-05-14T15:42:39.213273"
}
```

### **5.5. Логирование и мониторинг**

**Логирование:** Каждый запрос логируется с уровнем INFO. Логируются ошибки с уровнем ERROR.

**Метрики Prometheus:** http\_requests\_total (количество запросов), http\_request\_duration\_seconds (длительность), predictions\_total (предсказания по классам).

**Health Check:** Эндпоинт /health возвращает статус сервиса и информацию о загрузке модели.
