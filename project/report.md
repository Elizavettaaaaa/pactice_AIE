## 2. Постановка задачи и контекст

### 2.1. Предметная область и задача

Проект решает задачу бинарной классификации – прогнозирование оттока клиентов (customer churn prediction) телекоммуникационной компании. Потенциальный пользователь сервиса – маркетинговый отдел компании, который на основе предсказаний модели может своевременно предложить клиентам с высоким риском ухода индивидуальные условия удержания.

### 2.2. Формулировка задачи в терминах ML

**Входные данные:** исторические данные о клиенте, включая демографические характеристики, информацию о подключённых услугах, длительность обслуживания, способы оплаты и ежемесячные платежи.

**Целевая переменная:** бинарный признак Churn (1 – клиент ушёл, 0 – клиент остался).

**Ограничения:** модель должна обеспечивать высокую полноту (Recall), так как стоимость пропущенного уходящего клиента значительно выше стоимости ошибочного предложения лояльному клиенту. Время ответа API не должно превышать 1 секунду.

### 2.3. Целевые метрики качества

| Метрика | Целевое значение | Обоснование |
|---------|------------------|-------------|
| Recall | ≥ 0.75 | Приоритет – найти максимальное число уходящих клиентов |
| F1-score | ≥ 0.60 | Интегральный показатель качества |
| ROC-AUC | ≥ 0.80 | Оценка разделяющей способности модели |

Accuracy не является приоритетной метрикой из-за дисбаланса классов (26.5% ушедших).

## 3. Данные

### 3.1. Источник данных

Использован открытый датасет **Telco Customer Churn**, доступный на платформе Kaggle.

**Ссылка:** https://www.kaggle.com/datasets/blastchar/telco-customer-churn

### 3.2. Структура данных

| Параметр | Значение |
|----------|----------|
| Количество наблюждений | 7043 |
| Количество признаков | 21 |
| Числовые признаки | 4 (tenure, MonthlyCharges, TotalCharges, SeniorCitizen) |
| Категориальные признаки | 15 |
| Целевая переменная | Churn (0 – не ушёл, 1 – ушёл) |

**Список категориальных признаков:** gender, Partner, Dependents, PhoneService, MultipleLines, InternetService, OnlineSecurity, OnlineBackup, DeviceProtection, TechSupport, StreamingTV, StreamingMovies, Contract, PaperlessBilling, PaymentMethod.

### 3.3. Предобработка и EDA

**Основные шаги предобработки:**
1. Преобразование целевой переменной (Yes/No → 1/0)
2. Преобразование TotalCharges в числовой тип
3. Обработка пропусков с помощью SimpleImputer (медиана для числовых, most_frequent для категориальных)
4. One-Hot Encoding категориальных признаков (15 → 30 признаков)
5. Масштабирование числовых признаков (StandardScaler)

**Ключевые выводы EDA:**
- **Дисбаланс классов:** 73.5% / 26.5% (требует использования специальных метрик и механизмов коррекции)
- **Пропуски:** только в TotalCharges (0.16%), заполнены медианой
- **Ключевые признаки:** Contract, tenure, InternetService, PaymentMethod
- **Корреляции:** tenure (-0.35) и тип контракта (-0.30) сильнее всего связаны с оттоком

**Ноутбук с EDA:** `notebooks/01_Telco_EDA_and_Preprocessing.ipynb`

## 4. Модели и подходы

### 4.1. Базовые (baseline) модели

| Модель | Результат (F1) | Комментарий |
|--------|----------------|-------------|
| Logistic Regression (упрощённые признаки) | 0.63 | Recall = 58%, недостаточно для бизнес-задачи |
| Константный классификатор (все → 0) | 0 | Accuracy = 73.5%, но Recall = 0% |

**Вывод:** базовая модель превосходит тривиальную стратегию, но низкий Recall (58%) обосновывает необходимость более сложных моделей.

### 4.2. Улучшенные модели и эксперименты

Обучены и сравнены 6 моделей с учётом дисбаланса классов:

| Модель | Механизм борьбы с дисбалансом |
|--------|-------------------------------|
| Logistic Regression | class_weight='balanced' |
| Decision Tree | class_weight='balanced' |
| Random Forest | class_weight='balanced' |
| Gradient Boosting | — |
| XGBoost | scale_pos_weight = 2.77 |
| CatBoost | auto_class_weights='Balanced' |

**Подбор гиперпараметров:**
- XGBoost: GridSearchCV (n_estimators, max_depth, learning_rate) → лучшие параметры: learning_rate=0.05, max_depth=4, n_estimators=200
- CatBoost: GridSearchCV (iterations, depth, learning_rate) → лучшие параметры: depth=6, iterations=200, learning_rate=0.05

### 4.3. Дополнительные эксперименты (ноутбук 03)

**TimeSeriesSplit (временная валидация):**
- Данные отсортированы по признаку tenure
- Исследовано влияние test_size от 400 до 1400
- Оптимальное значение: test_size = 1400
- Результат: F1 ≈ 0.45, что подтверждает устойчивость к временному дрейфу

**SMOTE (синтетическая балансировка):**
- Применён для борьбы с дисбалансом классов
- Результат: SMOTE не улучшил качество (лучший результат после SMOTE – CatBoost с F1 = 0.5998)
- **Вывод:** встроенные механизмы коррекции дисбаланса эффективнее SMOTE

**Ноутбуки с экспериментами:**
- `notebooks/02_Telco_Model_Training.ipynb` – обучение и сравнение моделей
- `notebooks/03_Advanced_Validation_and_Balancing.ipynb` – TimeSeriesSplit и SMOTE

## 5. Экспериментальный протокол и результаты

### 5.1. Экспериментальный протокол

- **Разделение выборки:** train/test = 80/20 со стратификацией по целевой переменной
- **Кросс-валидация:** 5-fold для подбора гиперпараметров
- **Метрики:** Accuracy, Precision, Recall, F1-score, ROC-AUC

### 5.2. Сравнение моделей по метрикам

| Модель | Accuracy | Precision (1) | Recall (1) | F1-score (1) | ROC-AUC |
|--------|----------|---------------|------------|--------------|---------|
| Logistic Regression | 0.7388 | 0.5052 | 0.7834 | 0.6143 | 0.8417 |
| Decision Tree | 0.7410 | 0.5121 | 0.5107 | 0.5114 | 0.6679 |
| Random Forest | 0.7991 | 0.6619 | 0.4973 | 0.5679 | 0.8232 |
| Gradient Boosting | 0.7991 | 0.6542 | 0.5160 | 0.5770 | 0.8427 |
| XGBoost | 0.7594 | 0.5361 | 0.6952 | 0.6054 | 0.8316 |
| CatBoost | 0.7551 | 0.5262 | 0.7781 | 0.6278 | 0.8425 |
| **XGBoost (tuned)** | **0.7544** | **0.5244** | **0.8048** | **0.6350** | **0.8422** |
| CatBoost (tuned) | 0.7530 | 0.5231 | 0.7888 | 0.6290 | 0.8450 |

### 5.3. Выбор финальной модели

**Финальная модель:** XGBoost с подбором гиперпараметров

**Параметры:**
- learning_rate = 0.05
- max_depth = 4
- n_estimators = 200

**Метрики на тестовой выборке:**
- F1-score = 0.6350
- Recall = 80.5%
- Precision = 52.4%
- ROC-AUC = 0.842

**Trade-off:** снижение Precision (с 68% в базовом эксперименте до 52%) является сознательным компромиссом для достижения высокого Recall (80.5%). Это соответствует бизнес-приоритету – найти максимальное число уходящих клиентов, даже ценой ошибочных предложений лояльным клиентам.

## 6. Архитектура решения и сервис

### 6.1. Архитектура пайплайна

```

### 6.2. API и endpoints

| Эндпоинт | Метод | Описание |
|----------|-------|----------|
| `/` | GET | Информация о сервисе |

| `/docs` | GET | Swagger документация |
| `/metrics` | GET | Метрики для Prometheus |
| `/predict` | POST | Предсказание для одного клиента |
| `/predict_batch` | POST | Массовое предсказание |

**Пример запроса к `/predict`:**
```json
{
  "gender": "Female",
  "SeniorCitizen": 0,
  "Partner": "Yes",
  "tenure": 24,
  "MonthlyCharges": 85.5,
  "TotalCharges": 2052.0,
  ...
}

**Пример ответа:**
```json
{
  "prediction": 0,
  "probability": 0.3515,
  "threshold": 0.5,
  "class_label": "Не ушли",
  "timestamp": "2026-05-28T12:00:00"
}
```
